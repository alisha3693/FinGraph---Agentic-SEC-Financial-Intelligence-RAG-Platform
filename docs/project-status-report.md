This is a working audit of the current codebase (FastAPI + LangGraph agent in `multihop-rag/`, React dashboard in `frontend/`), not a wishlist. - **2026-10-08 — Replaced keyword routing with one AI "understand" step; added computed facts and a number check to single-company answers, closing verdicts, filing-type scoping, and model reranking. Not yet tested live: Groq's daily token limit is still used up.** All changes are in [graph_agent.py](../multihop-rag/graph_agent.py).
  1. **`understand_node`** replaces `router_node` (comparison keyword list) and `classify_node`. One LLM call per question, the same cost as before, gets the loaded-company list and returns: companies (or "all loaded companies"), whether it is a comparison, metrics needed, year range or "last N years", whether it needs figures, filing text, or both, whether it asks for a verdict, and the filing type and whether it wants the most recent one.   3. **Number check** (`_grounded_invoke`): after a financial answer, every figure with a decimal, %, x, or $ is compared with the table and computed facts at the precision shown. If any don't match, the model is asked once more, naming them, and the answer with fewer unmatched figures is kept. This applies to single-company and comparison answers. The comparison prompt now also includes the question itself, which it previously lacked.
  4. **Verdicts**: when the plan says the question asks "which one", the financial and qualitative comparison prompts require a closing "Verdict:" bullet. This targets Q51 and Q52.
  5. **Retrieval**: the diagnosis showed the right passages usually exist but rank 5–12 (Q54: Azure competition at rank 12; Q28: critical estimates at ranks 3 and 11; Q25 and Q24: boilerplate and 10-Q text ahead of the 10-K sections). Retrieval now fetches a pool of 12 candidates per company (8 when there are more than three companies), and one `_rerank` LLM call picks the best ones from 500-character snippets. The model's picks are validated and topped up from fusion order, and fusion order is kept if the call fails. A question naming a filing type ("most recent 10-K") is scoped to that filing, falling back to all of the company's chunks if none match. Checked offline: Q24's pool is now only Microsoft's 2026-07-29 10-K.
  - **Cost**: one extra rerank call per question (about 2k tokens). The routing test (`scratchpad/route_test.py`) runs only the understand step on all 60 questions and is ready to run when the daily limit resets.

Same gap for GM, F, T, and any other real 1-2 letter ticker. Verified live: `find_unloaded_ticker_candidates("What was KO revenue in 2025?", exclude=set())` returns `[]`; the equivalent query naming a 3+-letter-ticker company by name (Nike/NKE) correctly returns the specific not-ingested message. Lowering the length floor would need care — very short all-caps words are also common English abbreviations/acronyms (the length-3 floor was presumably a deliberate guard against exactly that), so this isn't a one-line fix.

- [ ] **"Profit margin" queries silently become plain Net Income, not a margin.** `METRIC_KEYWORDS` maps `"profit margin"` → `net_income` only ([graph_agent.py:39](../multihop-rag/graph_agent.py#L39)), consumed by `_select_metrics`. A query like "how has Apple's profit margin changed" gets a Net Income-only table (no Revenue), so the LLM narrative in `financial_analysis_node` ([graph_agent.py:462-489](../multihop-rag/graph_agent.py#L462-L489)) has no denominator to compute an actual margin from — any margin percentage it states is not grounded in the table it was given. Margin/ratio metrics (`net_income/revenue`, `liabilities/assets`, etc.) don't exist as first-class columns anywhere in the schema.

- [ ] **Default trend chart can plot EPS on the same axis as figures 50–100x larger.** The default all-metrics overview (`get_default_financials`, [graph_agent.py:402-419](../multihop-rag/graph_agent.py#L402-L419)) always includes all 5 metrics on one `TrendChart`. Revenue/Assets/Liabilities are in $B (e.g. ~390) while EPS is a raw dollar figure (e.g. ~6.1); on a shared linear y-axis the EPS line is visually flattened to the bottom and unreadable. Needs either a secondary axis, per-series normalization, or excluding EPS from the shared-scale default chart.

- [ ] **No automated tests exist.** Nothing in `multihop-rag/` or `frontend/` has test coverage — not the router's keyword logic, not `_extract_year_range`, not `_select_metrics`, not the ingestion parsing in `sec_client.py`. Given how much of the routing behavior is regex/keyword-based (see §3), this is the highest-leverage gap: a small `pytest` suite over `_select_metrics`, `_extract_year_range`, `_find_matching_tickers`, and `router_node` would catch regressions cheaply since none of it needs network/LLM calls.

- [ ] **A stalled Hugging Face Hub request during startup hangs the entire backend, forever, with zero visible symptom other than every route timing out.** `get_embeddings()` ([vector_store.py:11-14](../multihop-rag/vector_store.py#L11-L14)) is warmed inside the FastAPI `lifespan` ([app.py:22-32](../multihop-rag/app.py#L22-L32)) *before* uvicorn starts serving any request. `HuggingFaceEmbeddings`/`sentence-transformers` makes a cascade of live HEAD/GET calls to `huggingface.co` on every single process start (confirmed directly in a clean restart's log: `modules.json`, `config_sentence_transformers.json`, `config.json`, `tokenizer_config.json`, `README.md`, `1_Pooling/config.json`, plus a couple of 404 probes) — even though the model is already cached locally. There is no timeout around this call and no `HF_HUB_OFFLINE`/`local_files_only` set anywhere. Observed directly on 2026-08-25: the server process was alive, listening on port 8000, 13MB resident / near-zero CPU (i.e. stuck in network I/O wait, never finished startup) — and because lifespan startup gates the whole app, even `/api/health` timed out. **Fix:** set `HF_HUB_OFFLINE=1` (and/or `local_files_only=True` in `HuggingFaceEmbeddings`) once the model is cached, and/or wrap the warm-up call in a timeout so a Hub outage degrades instead of hanging the process indefinitely.

- [x] ~~A segfault (exit code 139) crashed the whole backend the first time any new ticker's filings were actually embedded.~~ **Fixed 2026-08-30.** `get_embeddings()` ([vector_store.py](../multihop-rag/vector_store.py)) only constructed the model at startup, never ran a real forward pass — so the model's first genuine embedding computation happened lazily, off the main thread (inside a FastAPI sync-route worker thread), the first time a ticker was actually ingested. On Windows, PyTorch's native BLAS/OpenMP thread pool initializing off the main thread is a known cause of a hard interpreter segfault. Fix: `get_embeddings()` now runs a real `embed_query("warmup")` call itself, forcing that one-time native init to happen during startup on the main thread. See §0 for full detail and verification.

- [ ] **A hung/unreachable backend is indistinguishable from "no companies loaded" in the UI.** `fetchCompanies()` in [App.jsx](../frontend/src/App.jsx) only does `console.error(...)` on a failed fetch — no error state is set, so the sidebar silently renders the same "No companies ingested yet." empty state whether the DB is genuinely empty or the backend is just unreachable/hung (as in the incident above). This is exactly what made a live backend hang look like data loss. **Fix:** track a `companiesError` state distinct from an empty list, and show a "Can't reach the backend" message instead of the empty-watchlist copy when the fetch itself failed.

- [ ] **LLM provider errors surface as a bare HTTP 500 with no readable message.** The LLM nodes (`filing_rag_node`, `financial_analysis_node`, `comparison_*`, `mixed_node` via its children, `external_queries_node`) don't catch exceptions from Groq. A removed model (`404 model_not_found`, as on 2026-10-04) or a rate limit (`429`) fails the whole `/api/query` request with a generic 500, and the frontend has nothing to show. `classify_node` has a fallback, but that fallback is also what hid the missing `chain` bug above. Planned: catch provider errors at the graph or `app.py` boundary and return a readable answer, with the error logged.

- [ ] **Backend does not fit on Render's 512 MB instance.** Startup alone measures ~543 MB resident (torch + sentence-transformers + chromadb + LangGraph + the embedding model), so Render kills the process with `Out of memory (used over 512Mi)` before it binds a port. Decision needed: upgrade the instance to 2 GB, or swap to a lighter embedding runtime (e.g. ONNX `fastembed`) with a full re-index and retrieval re-test.

Original report: comparison tables show a missing year as $0.00, and the narrative treats it as a real collapse. `comparison_financial_result` ([graph_agent.py](../multihop-rag/graph_agent.py)) reads a missing `(ticker, year, metric)` as zero (`.get(yr, {}).get(m, 0)`). - [ ] **A classifier failure on a comparison query silently drops the numeric half.** When `classify_node`'s call fails, it defaults to qualitative only, even for a comparison that needs the numbers. §7.3.1 Q31 hit this: the answer said the data was missing, though the numeric path had the data. - [ ] **Groq's output-token rate limit (1,000 per minute) breaks bursts of calls.** Each query makes two or three LLM calls with up to 900 output tokens each. A burst of comparison questions exceeds the limit. The runner retries the whole query, but the app has no retry and no pacing. Q32 hit this once in the re-run and succeeded on retry.

- [ ] **Single-hop retrieval despite the "multihop-rag" name.** There is exactly one `retriever.invoke(query)` call per question inside `filing_rag_node` — no query decomposition, no iterative "retrieve → check if enough → retrieve again" loop. The combined-answer half of this item is **fixed as of 2026-09-14** (§0): the new LLM-based `classify_node` correctly classifies causal phrasing like "why did revenue grow in 2024" or "what drove the increase in net income" as needing both `needs_financial` and `needs_qualitative` (verified live — see §0), so it now reaches `mixed_node` and gets both the numeric trend and the actual MD&A prose that explains "why," instead of routing to numbers alone. - [ ] **`k=4` is fixed and not configurable.** [graph_agent.py:516](../multihop-rag/graph_agent.py#L516) hardcodes retrieval depth; no env var, no query-complexity-based scaling. (`comparison_qualitative_result`'s per-company `k=3` has the same fixed-not-configurable issue.)

- [ ] **No reranking or diversity control.** `db.as_retriever` uses default similarity search, not MMR ([graph_agent.py:515-518](../multihop-rag/graph_agent.py#L515-L518)) — the 4 chunks returned can be near-duplicates from the same section of the same filing rather than a diverse spread of relevant passages.

## 4. Chat Context & Sessions

**Current state: none.** This is worth calling out explicitly since it's easy to assume the "agent"/LangGraph framing implies memory — it doesn't here.

- `POST /api/query` ([app.py](../multihop-rag/app.py)) takes only `{prompt}` — no ticker, no session/conversation id (the ticker field was removed 2026-09-12, see §0 — every query resolves its company from the prompt text alone now).
- `run_agent()` ([graph_agent.py](../multihop-rag/graph_agent.py)) builds a brand new `AgentState` per call with no prior turns folded in.
- The LangGraph graph is compiled with `builder.compile()` and no checkpointer ([graph_agent.py:958](../multihop-rag/graph_agent.py#L958)) — LangGraph supports `MemorySaver`/thread-based checkpointing, but none is wired up, and `langgraph`'s checkpoint packages aren't even in `requirements.txt`.
- The frontend only ever holds one `currentResponse` ([App.jsx](../frontend/src/App.jsx)) — asking a new question discards the previous answer entirely. There is no visible thread, no follow-up resolution ("what about last year?", "and Microsoft?") — a follow-up with a pronoun or omitted subject will either mis-route or trigger `_resolve_ticker_or_clarify`'s ambiguous-company clarification ([graph_agent.py:175-218](../multihop-rag/graph_agent.py#L175-L218)) instead of using the prior turn's company.
- Nothing persists across questions today, by design — see the 2026-09-12 changelog entry on removing the UI-side ticker pin.

**Proposed plan** (roughly in order):
1. Add a `session_id` (generated client-side, stored in `localStorage`, sent with every `/api/query` call).
2. Add a `langgraph.checkpoint.memory.MemorySaver` (in-process is fine for a single-instance deployment) keyed by `session_id`, so `_GRAPH.invoke` can carry state across turns.
3. Track a small resolved-entity memory per session (last ticker, last metrics, last year range) and let `_resolve_ticker_or_clarify` and `_select_metrics` fall back to it instead of only the current message.
4. Frontend: keep a list of past `{prompt, response}` turns per session and render them as a scrollable thread instead of a single `currentResponse`.
5. Add a "New session" / clear-context action so a stale pinned ticker/metric doesn't leak into an unrelated question.

## 7. Example Prompts — 60 Reference Queries

Four sets of 15. §7.1–7.2 (original 30, 2026-09-13) are single-company: qualitative *analysis* of the 5 quantitative DB metrics (interpretation, trend characterization, comparative judgment), and genuine qualitative *text* analysis over indexed filing content (risk factors, MD&A, business overview). §7.3 (added 2026-09-14) is cross-company: the same numeric-vs-narrative split, but exercising the comparison path added the same day. See each set's own intro for which node/data source it exercises.

### 7.1 Qualitative Analysis of DB Metrics

Reference set (2026-09-13) for exercising `financial_analysis_node`/`comparison_node`'s narrative-generation path. All 15 are answerable purely from the five structured SQLite fields ([sec_client.py](../multihop-rag/sec_client.py) `metric_tags`: `revenue`, `net_income`, `eps`, `assets`, `liabilities`) — they ask for the kind of interpretive, professional judgment a real analyst gives *about* numbers (trend characterization, sustainability, risk, comparative positioning), not just the numbers read back. This is qualitative analysis *of quantitative data*, distinct from qualitative *text* analysis (risk factors, MD&A prose), which instead requires `filing_rag_node` over the Chroma-indexed filing chunks — a separate data source these prompts don't touch.

**Growth & momentum**
1. How has Apple's revenue growth trajectory evolved over the past five years — is momentum accelerating or decelerating?
2. Does NVIDIA's recent revenue growth look sustainable, or does the data suggest a one-time spike?

**Profitability & margin quality**
3. Is Tesla's net income growth keeping pace with its revenue growth, or are margins compressing?
4. Is Apple's EPS growth consistent with its net income growth, or is there a divergence worth flagging?

**Balance sheet strength & leverage**
5. What does Microsoft's asset-to-liability ratio over time suggest about its balance sheet strength and financial risk?
6. How would you characterize Amazon's leverage profile based on liabilities relative to assets over the last several years?
7. How has Microsoft's balance sheet evolved — is asset growth outpacing liability growth, or the reverse?
8. What does Amazon's liabilities-to-assets trend suggest about its financial risk as it scales?
