# FinGraph — Project Status Report & Checklist

_Last updated: 2026-09-04 · Branch: `ticker-fix`_

This is a working audit of the current codebase (FastAPI + LangGraph agent in `multihop-rag/`, React dashboard in `frontend/`), not a wishlist. Every item below is tied to a real file/line so it can be picked up without re-deriving context. There are currently **zero automated tests** anywhere in the repo (`multihop-rag/`, `frontend/`) — keep that in mind when prioritizing: several fixes below are risky to make blind.

This doc is kept live: every change made to the project (fix, feature, redesign, or incident) gets logged in §0 and reflected in the relevant checklist below in the same pass, not as a separate follow-up step.

## 0. Changelog

- **2026-09-04 — Restyled scrollbars app-wide (slim, transparent track, theme-matched) and fixed a stray horizontal scrollbar on the sidebar.** Requested UI polish: default OS scrollbars looked out of place against the restrained "financial workstation" theme. Added `--scrollbar-thumb`/`--scrollbar-thumb-hover` tokens (a low-opacity tint of `--text-primary`, inverted per theme like every other token) and a global rule set in [index.css](../frontend/src/index.css) — `scrollbar-width: thin; scrollbar-color: var(--scrollbar-thumb) transparent;` for Firefox, and `::-webkit-scrollbar`/`-track`/`-thumb`/`-corner` for Chrome/Edge/Safari (9px wide, thumb padded off the track edge via a transparent border + `background-clip: content-box` so it reads as a slender floating pill, not a solid OS-default bar). Applies to every scrollable region: `.sidebar`, `.content-column`, `.chart-column`, `.data-table-scroll`, `.citation-text`, the stacked `.workspace`. **Also found and fixed while verifying this**: `.sidebar` had a stray *horizontal* scrollbar (screenshot from the user showed classic Windows arrow-button scrollbar UI at its bottom edge, clipping the ticker-ingest input). Root cause: `.field-input` (the ticker input) is a flex item inside `.ticker-form` with no `min-width` set — flex items default to `min-width: auto` (their intrinsic content width), which can exceed the 248px sidebar's available space and force horizontal overflow. Fix: `min-width: 0` on `.field-input`, plus `overflow-x: hidden` on `.sidebar` itself as a safety net against any future stray overflow. **Verified live**: `.sidebar.scrollWidth` now equals `.clientWidth` (237px both, no overflow) via a headless-Chrome check against the running container, and screenshots in both themes confirm the new scrollbar renders as a thin, low-contrast pill that blends into the surface instead of a hard-edged OS bar.
- **2026-09-04 — Fixed a follow-up bug in the same scroll-containment fix: long answers were silently clipped with no scrollbar at all, instead of scrolling.** After the page-level-scroll fix below, the user reported the response area still cut off content (visible in a real screenshot: a 9-row table truncated at row 7, no "Analysis" section, no citations, no scrollbar anywhere) even after a hard refresh. Root cause, found by driving a live headless Chrome instance against the real backend response and comparing `getBoundingClientRect().height` (369px, visually clipped) against `scrollHeight` (1025px, true content height) on `.answer-block`: both `.answer-block` and `.data-table-wrap` ([index.css](../frontend/src/index.css)) have `overflow: hidden` (only intended to clip their own rounded corners) while also being direct flex children of `.content-column` (a column flex container). Per the CSS flexbox spec, a flex item's automatic minimum size becomes `0` instead of its content size specifically when the item's own overflow is non-`visible` — so instead of `.content-column`'s `overflow-y: auto` detecting the overflow and scrolling, the browser was silently shrinking `.answer-block`/`.data-table-wrap` down to fit the available space and clipping everything past that point via their own `overflow: hidden`, with `.content-column.scrollHeight` never reflecting the true content height. **Fix:** added `flex-shrink: 0` to both `.answer-block` and `.data-table-wrap` so they can no longer be compressed below their natural content height, forcing `.content-column` to correctly detect the overflow and scroll instead. **Verified live**: `.content-column`'s `scrollHeight` (1002px) now correctly exceeds its `clientHeight` (417px) for a real NVDA query response, a scrollbar renders, scrolling it moves `scrollTop` and reveals the full analysis text + citations, and `.navbar`/`.query-bar` positions stayed pixel-identical throughout (still pinned, per the fix below). Restarted the frontend container again to pick up the change (same bind-mount HMR gotcha noted below).
- **2026-09-04 — Fixed the query response area requiring a page-level scroll past the prompt bar to see it.** `body`/`#root` ([index.css](../frontend/src/index.css)) previously only set `min-height: 100vh` with no `overflow: hidden`, so the whole page grew with the content and scrolled as one block — the navbar and the bottom `.query-bar` (prompt input) scrolled out of view along with a long answer instead of staying put. **Fix:** `body`/`#root` are now locked to `height: 100vh; overflow: hidden`, `.layout`/`.main`/`.workspace` propagate `overflow: hidden` down the flex/grid chain, and `.content-column` (where the answer/table/citations render) is the one region with `overflow-y: auto` — so `.navbar` (top) and `.query-bar` (bottom, `flex-shrink: 0`) now stay visually static while only the response scrolls. `.chart-column` is unaffected (stays fully visible alongside the scrolling response) per the request; below the 1200px stacked-layout breakpoint the whole `.workspace` scrolls together instead (a per-column fixed-height scroll region doesn't work once the two columns stack vertically). **Verified live** via headless Chrome driven directly over the DevTools protocol (no `chromium-cli`/Playwright installed in this environment): clicked a watchlist company, injected a forced-overflow block into `.content-column`, and confirmed via `getBoundingClientRect()` that `.navbar`/`.query-bar` positions were pixel-identical before and after scrolling `.content-column` to its end, `document.body.scrollHeight` stayed pinned at the viewport height (804px, never grew to the content's 9041px), and `window.scrollY` stayed 0 throughout — only `.content-column`'s own `scrollTop` moved. Screenshots confirm the same visually. **Dev-workflow gotcha hit during verification:** the frontend runs via the `ragproject-frontend` Docker container ([docker-compose.yml](../docker-compose.yml), bind-mounted `./frontend:/app`); Vite's file watcher inside the container did not pick up this edit made from the Windows host — computed styles kept reflecting the pre-edit CSS even after a hard page reload, because Vite's dev-server module cache isn't invalidated without a working file-change event, and inotify events don't reliably propagate through a Windows-host-to-WSL2-container bind mount. Had to `docker compose restart frontend` before the change took effect in the browser. **If a frontend edit doesn't seem to apply, restart the frontend container before assuming the code is wrong.**
- **2026-09-04 — Fixed "SEC returned no annual financial facts" for Microsoft (and any non-calendar-fiscal-year company).** `_annual_value` ([sec_client.py:75-118](../multihop-rag/sec_client.py#L75-L118)) matched a fact to a year by requiring its literal `start`/`end` dates to equal `{year}-01-01`/`{year}-12-31` — an assumption that every company's fiscal year is the calendar year. Microsoft's fiscal year runs July 1 → June 30 (confirmed directly against SEC's companyfacts API: MSFT's FY2024 `NetIncomeLoss` entry is `start=2023-07-01, end=2024-06-30`), so it never had a matching entry and `parse_financials` silently returned `{}` for every year, tripping the "no annual financial facts" error in `load_company_data` ([sec_client.py:280](../multihop-rag/sec_client.py#L280)). This affected any ticker with a non-calendar fiscal year, not just MSFT (e.g. Apple's FY ends late September). **Fix:** bucket annual facts by the calendar year the fact's own `end` date falls in (matching how companies label their own fiscal years) instead of requiring literal Jan 1–Dec 31 bounds, with a ~340+ day duration check for non-instant metrics; also relaxed the instant-value frame regex from `CY\d{4}Q4I` to `CY\d{4}Q\dI` so non-Q4 fiscal year-ends still get correct frame-based tie-breaking. **Verified** directly against live SEC data: MSFT now resolves 9 years (2018–2026) of Revenue/Net Income/EPS/Assets/Liabilities; re-ran Coca-Cola (calendar fiscal year) and Apple (non-calendar, FY ends September) as a regression check — both still resolve correctly, 8 years each, no change in behavior for calendar-fiscal-year companies.
- **2026-09-01 — Fixed multi-year revenue (and other metric) values silently coming back `0` for some fiscal years — reported live for TSLA's 2019–2022 revenue.** Root cause was two compounding bugs in [`parse_financials`/`_annual_value`](../multihop-rag/sec_client.py#L71-L119): (1) `_annual_value` matched a fact to a year via `entry["fy"]`, which is the fiscal year *of the filing the value was reported in*, not the year the value covers — a 10-K's prior-year comparative figures carry the *current* filing's `fy` (confirmed directly against SEC's companyconcept API: Tesla's FY2021/2022 revenue is tagged `fy=2023` inside its FY2023 10-K), so any year later restated as a comparative silently failed to match; (2) `parse_financials`'s tag-fallback loop broke out after the *first* tag filled *any* year, so once `RevenueFromContractWithCustomerExcludingAssessedTax` filled only 2018 (its only cleanly-`fy`-matching year for Tesla), the `Revenues` fallback tag — which actually has clean 2017–2023 coverage — was never tried, leaving 2019–2022 unfilled → stored as `NULL` → rendered as `0`. **Fix:** `_annual_value` now matches a fact's *own* `start`/`end` period dates against the target year instead of `fy`/`fp`, and prefers SEC's `frame`-stamped entry (`CY\d{4}` / `CY\d{4}Q4I`) — the one de-duplicated canonical value per period — as a tiebreaker; the tag loop in `parse_financials` now only stops once *every* year is covered, not once any single year is. Verified directly against Tesla's live SEC companyconcept data (both `Revenues` and `RevenueFromContractWithCustomerExcludingAssessedTax`) before and after: fixed logic now correctly resolves 2019=$24.578B, 2020=$31.536B, 2021=$53.823B, 2022=$81.462B (previously `None` for all four). **Backfilled and verified:** restarted the backend (PID 28068 → new process; it doesn't hot-reload code, `RELOAD` is off by default) so the fixed logic was actually loaded, then re-ran `POST /api/load_ticker` for TSLA. Confirmed via `GET /api/financials/TSLA`: revenue is now 2018=$21.46B, 2019=$24.58B, 2020=$31.54B, 2021=$53.82B, 2022=$81.46B, 2023=$96.77B — all real values, no `0`s. Other previously-ingested tickers (AMZN, NVDA, MSFT, AAPL) were not re-ingested and should be spot-checked / re-added if they show the same gap for any metric/year.
- **2026-08-30 — Disabled uvicorn auto-reload by default after it wedged the backend mid-ingest.** Live incident: after adding a new ticker, the backend (PID 5140) was alive and still `LISTEN`ing on :8000 but every request — including `/api/health`, which does no work — hung with no response, at ~0% CPU, and no writes to `chroma_db/` or `sec_financials.db` for ~5 min. Diagnosis: `python app.py` ran `uvicorn.run(..., reload=True)`, so PID 5140 was the reload **supervisor** holding the socket while a forked **child** did the serving; only one `python.exe` was present, i.e. the child had died (native crash, not a Python exception — those return HTTP 500) mid-ingest, matching the last DB write time. A re-fork landing while the torch/OpenMP thread pool initializes is the trigger. **Fix:** [app.py](../multihop-rag/app.py) `__main__` no longer passes `reload=True` unconditionally — it now reads `RELOAD` env var (default off), so `python app.py` runs a single process with no reload child. Killed PID 5140, restarted; `/api/health` OK, `/api/companies` returns the 5-ticker watchlist (AMZN, TSLA, NVDA, MSFT, AAPL). The ticker that triggered the crash did not finish ingesting and needs to be re-added. Related to but distinct from the 2026-08-25 hung-backend entry (that one never finished lifespan startup; this one started fine and lost its worker later). Also updated [codebase-walkthrough.md](codebase-walkthrough.md) §8 (new `RELOAD` env var documented) and §9 (run command changed from `uvicorn … --reload` to `python app.py`). Note: running `python app.py` a second time while one is already up gives `[Errno 10048] … only one usage of each socket address` — that is just the port-8000 already bound by the live process, not a new fault; check the port owner (`Get-NetTCPConnection -LocalPort 8000`) before starting another.
- **2026-08-30 — Diagnosed and fixed a mid-ingest backend segfault (exit code 139).** Live incident: `POST /api/load_ticker` for a *new* ticker reliably crashed the whole Python process (not a hang — `Segmentation fault`, confirmed via the uvicorn process log) right as the first filing chunk was embedded. Root cause: `get_embeddings()` ([vector_store.py](../multihop-rag/vector_store.py)) only *constructed* the HuggingFace/sentence-transformers model at startup — it never ran an actual forward pass — so the model's real first embedding computation was happening lazily, later, inside whichever thread called it first. In practice that was a FastAPI request-handler worker thread (sync routes are dispatched off the main thread), the first time a ticker was ingested. On Windows, PyTorch's native BLAS/OpenMP thread pool initializes lazily on that first real forward pass, and initializing it off the main thread is a known cause of a hard interpreter segfault rather than a catchable Python exception. **Fix:** `get_embeddings()` now runs one real `embed_query("warmup")` call itself, so the one-time native init happens during `app.py`'s startup (`lifespan`, main thread, before any request is served) instead of racing with the first real request. Also added a defensive `os.environ.setdefault("KMP_DUPLICATE_LIB_OK", "TRUE")` at the very top of [app.py](../multihop-rag/app.py) (before any transitive `torch` import) to tolerate a duplicate-OpenMP-runtime scenario, a related but distinct Windows native-library issue — this alone did not fix the crash (verified: still segfaulted with only this change), the thread-affinity warm-up fix above is what actually resolved it. **Verified**: ingested a fresh ticker (`GOOGL`, not previously loaded, to force a full cold embedding pass) end-to-end with no crash (342 chunks indexed, HTTP 200, server still healthy afterward), then removed it again since it was only a test — the watchlist (AMZN, TSLA, NVDA, MSFT) is unchanged from before this fix.
- **2026-08-30 — Fixed wasteful full re-embed on every ticker re-ingest.** `ingest_filings()` ([sec_client.py](../multihop-rag/sec_client.py)) previously deleted and re-downloaded/re-embedded all 12 filings on every `load_ticker` call, even for an already-loaded company with no new filings. Now diffs against `accession_number` already stored in each chunk's metadata: filings that dropped out of the current top-12 window are pruned, already-indexed filings are skipped entirely (no re-download, no re-embed), and only genuinely new filings are processed. Closes the "no diffing" item in §2.
- **2026-08-30 — Fixed unreadable chart hover tooltip in dark mode.** [index.css](../frontend/src/index.css) `.chart-tooltip` derived its background from `var(--text-primary)` and its year-label color from `var(--bg-surface)` — both tokens deliberately invert between light/dark mode, but `.tooltip-row` (the line showing each series' name + value) was left hardcoded to `rgba(255,255,255,0.85)`. In light mode this accidentally worked (dark tooltip bg + white text); in dark mode `--text-primary` flips to near-white, turning the tooltip into a near-white box with near-white text — unreadable, as reported. Fix: added fixed, non-inverting `--tooltip-bg`/`--tooltip-text`/`--tooltip-text-muted` tokens (dark chip, light text in both themes — the standard pattern for floating chart tooltips) and pointed all three tooltip rules at them instead of the theme-flipping tokens.

## 1. Remaining Bugs (general)

- [ ] **Two-company "compare" always takes the numeric route, even for qualitative questions.** [graph_agent.py:216-223](../multihop-rag/graph_agent.py#L216-L223) routes to `comparison_node` the moment two tickers are matched, with no check for whether the question is even about numbers. "Compare Apple and Tesla's risk factors" or "compare their strategies" will still produce a Revenue/Net Income pivot table — because `comparison_node` ([graph_agent.py:406](../multihop-rag/graph_agent.py#L406)) has no qualitative path at all, it just defaults `metrics=["revenue","net_income"]` ([graph_agent.py:458](../multihop-rag/graph_agent.py#L458)) regardless of intent. The single-company path already guards this with `is_financial` ([graph_agent.py:224](../multihop-rag/graph_agent.py#L224)); the two-company path never got the same guard. See §4 for the fix.

- [ ] **"Profit margin" queries silently become plain Net Income, not a margin.** `_select_metrics` maps `"profit margin"` → `net_income` only ([graph_agent.py:40](../multihop-rag/graph_agent.py#L40)). A query like "how has Apple's profit margin changed" gets a Net Income-only table (no Revenue), so the LLM narrative in `financial_analysis_node` ([graph_agent.py:329-340](../multihop-rag/graph_agent.py#L329-L340)) has no denominator to compute an actual margin from — any margin percentage it states is not grounded in the table it was given. Margin/ratio metrics (`net_income/revenue`, `liabilities/assets`, etc.) don't exist as first-class columns anywhere in the schema.

- [ ] **Deleting the currently-selected company doesn't fall back to another one.** `handleDeleteCompany` in [App.jsx](../frontend/src/App.jsx) resets `selectedTicker` to `''` when you remove the active company, but — unlike `fetchCompanies`, which auto-selects `data[0].ticker` on initial load — it never re-selects the next available company. The default metric strip / chart / table all go blank until the user manually clicks another watchlist chip.

- [ ] **Default trend chart can plot EPS on the same axis as figures 50–100x larger.** The default all-metrics overview (`get_default_financials`, [graph_agent.py:273-288](../multihop-rag/graph_agent.py#L273-L288)) always includes all 5 metrics on one `TrendChart`. Revenue/Assets/Liabilities are in $B (e.g. ~390) while EPS is a raw dollar figure (e.g. ~6.1); on a shared linear y-axis the EPS line is visually flattened to the bottom and unreadable. Needs either a secondary axis, per-series normalization, or excluding EPS from the shared-scale default chart.

- [ ] **No automated tests exist.** Nothing in `multihop-rag/` or `frontend/` has test coverage — not the router's keyword logic, not `_extract_year_range`, not `_select_metrics`, not the ingestion parsing in `sec_client.py`. Given how much of the routing behavior is regex/keyword-based (see §3), this is the highest-leverage gap: a small `pytest` suite over `_select_metrics`, `_extract_year_range`, `_find_matching_tickers`, and `router_node` would catch regressions cheaply since none of it needs network/LLM calls.

- [ ] **A stalled Hugging Face Hub request during startup hangs the entire backend, forever, with zero visible symptom other than every route timing out.** `get_embeddings()` ([vector_store.py:11-14](../multihop-rag/vector_store.py#L11-L14)) is warmed inside the FastAPI `lifespan` ([app.py:22-32](../multihop-rag/app.py#L22-L32)) *before* uvicorn starts serving any request. `HuggingFaceEmbeddings`/`sentence-transformers` makes a cascade of live HEAD/GET calls to `huggingface.co` on every single process start (confirmed directly in a clean restart's log: `modules.json`, `config_sentence_transformers.json`, `config.json`, `tokenizer_config.json`, `README.md`, `1_Pooling/config.json`, plus a couple of 404 probes) — even though the model is already cached locally. There is no timeout around this call and no `HF_HUB_OFFLINE`/`local_files_only` set anywhere. Observed directly on 2026-08-25: the server process was alive, listening on port 8000, 13MB resident / near-zero CPU (i.e. stuck in network I/O wait, never finished startup) — and because lifespan startup gates the whole app, even `/api/health` timed out. **Fix:** set `HF_HUB_OFFLINE=1` (and/or `local_files_only=True` in `HuggingFaceEmbeddings`) once the model is cached, and/or wrap the warm-up call in a timeout so a Hub outage degrades instead of hanging the process indefinitely.

- [x] ~~A segfault (exit code 139) crashed the whole backend the first time any new ticker's filings were actually embedded.~~ **Fixed 2026-08-30.** `get_embeddings()` ([vector_store.py](../multihop-rag/vector_store.py)) only constructed the model at startup, never ran a real forward pass — so the model's first genuine embedding computation happened lazily, off the main thread (inside a FastAPI sync-route worker thread), the first time a ticker was actually ingested. On Windows, PyTorch's native BLAS/OpenMP thread pool initializing off the main thread is a known cause of a hard interpreter segfault. Fix: `get_embeddings()` now runs a real `embed_query("warmup")` call itself, forcing that one-time native init to happen during startup on the main thread. See §0 for full detail and verification.

- [ ] **A hung/unreachable backend is indistinguishable from "no companies loaded" in the UI.** `fetchCompanies()` in [App.jsx](../frontend/src/App.jsx) only does `console.error(...)` on a failed fetch — no error state is set, so the sidebar silently renders the same "No companies ingested yet." empty state whether the DB is genuinely empty or the backend is just unreachable/hung (as in the incident above). This is exactly what made a live backend hang look like data loss. **Fix:** track a `companiesError` state distinct from an empty list, and show a "Can't reach the backend" message instead of the empty-watchlist copy when the fetch itself failed.

## 2. RAG-Specific Bugs

- [ ] **`filing_rag_node` never filters by filing type or fiscal year, even when the question names one.** The Chroma filter is hardcoded to `{"company": ticker}` ([graph_agent.py:364-367](../multihop-rag/graph_agent.py#L364-L367)), even though every indexed chunk already carries `filing_type` and `fiscal_year` metadata ([sec_client.py:205-217](../multihop-rag/sec_client.py#L205-L217)). "What did the 2023 10-K say about supply chain risk" retrieves from whichever 4 chunks are semantically closest across *all* indexed 10-K/10-Q/8-K filings for that ticker — a 2024 8-K chunk can easily outrank the actual 2023 10-K passage the user asked for.

- [x] ~~Re-ingesting a ticker always re-downloads and re-embeds every filing, with no diffing.~~ **Fixed 2026-08-30.** `ingest_filings` ([sec_client.py:151-221](../multihop-rag/sec_client.py#L151-L221)) now diffs against `accession_number` in existing chunk metadata: filings that fell out of the current top-12 window are pruned, filings already indexed are left untouched, and only genuinely new filings are downloaded/embedded. Re-ingesting an already-loaded, unchanged company is now a near no-op instead of a full re-download-and-re-embed. `load_company_data`'s success message ([sec_client.py:255-258](../multihop-rag/sec_client.py#L255-L258)) now reports the total indexed chunk count (existing + new − pruned), not just what changed this call.

- [ ] **Single-hop retrieval despite the "multihop-rag" name.** There is exactly one `retriever.invoke(query)` call per question ([graph_agent.py:368](../multihop-rag/graph_agent.py#L368)) — no query decomposition, no iterative retrieval, and no path that combines structured SQLite facts with qualitative filing text in the same answer (e.g. "why did revenue grow in 2024" routes to `financial_analysis_node` and only ever sees numbers, never the MD&A prose that would actually explain "why").

- [ ] **`k=4` is fixed and not configurable.** [graph_agent.py:365](../multihop-rag/graph_agent.py#L365) hardcodes retrieval depth; no env var, no query-complexity-based scaling.

- [ ] **No reranking or diversity control.** `db.as_retriever` uses default similarity search, not MMR ([graph_agent.py:364-367](../multihop-rag/graph_agent.py#L364-L367)) — the 4 chunks returned can be near-duplicates from the same section of the same filing rather than a diverse spread of relevant passages.

## 3. RAG Optimization Opportunities

- [ ] **Add filing_type / fiscal_year filters to the Chroma query** when the question names them (a small regex similar to `_extract_year_range`, reused against `filing_type`/`fiscal_year` metadata already stored). Directly fixes the bug in §2.
- [ ] **Switch to MMR (`search_type="mmr"`)** in `filing_rag_node`'s retriever for better source diversity at the same `k`.

## 4. Chat Context & Sessions

**Current state: none.** This is worth calling out explicitly since it's easy to assume the "agent"/LangGraph framing implies memory — it doesn't here.

- `POST /api/query` ([app.py:53-55](../multihop-rag/app.py#L53-L55)) takes only `{prompt, ticker}` — no session/conversation id.
- `run_agent()` ([graph_agent.py:596-613](../multihop-rag/graph_agent.py#L596-L613)) builds a brand new `AgentState` per call with no prior turns folded in.
- The LangGraph graph is compiled with `builder.compile()` and no checkpointer ([graph_agent.py:590](../multihop-rag/graph_agent.py#L590)) — LangGraph supports `MemorySaver`/thread-based checkpointing, but none is wired up, and `langgraph`'s checkpoint packages aren't even in `requirements.txt`.
- The frontend only ever holds one `currentResponse` ([App.jsx](../frontend/src/App.jsx)) — asking a new question discards the previous answer entirely. There is no visible thread, no follow-up resolution ("what about last year?", "and Microsoft?") — a follow-up with a pronoun or omitted subject will either mis-route or trigger `_resolve_ticker_or_clarify`'s ambiguous-company clarification ([graph_agent.py:139-174](../multihop-rag/graph_agent.py#L139-L174)) instead of using the prior turn's company.
- The only thing that persists across questions today is the **UI-side ticker pin** (`selectedTicker` sent as `ticker_hint`) — that's a scoping mechanism, not conversation memory; it doesn't recall previous metrics, years, or comparisons discussed.

**Proposed plan** (roughly in order):
1. Add a `session_id` (generated client-side, stored in `localStorage`, sent with every `/api/query` call).
2. Add a `langgraph.checkpoint.memory.MemorySaver` (in-process is fine for a single-instance deployment) keyed by `session_id`, so `_GRAPH.invoke` can carry state across turns.
3. Track a small resolved-entity memory per session (last ticker, last metrics, last year range) and let `_resolve_ticker_or_clarify` and `_select_metrics` fall back to it instead of only the current message.
4. Frontend: keep a list of past `{prompt, response}` turns per session and render them as a scrollable thread instead of a single `currentResponse`.
5. Add a "New session" / clear-context action so a stale pinned ticker/metric doesn't leak into an unrelated question.
